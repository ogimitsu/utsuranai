# 設計判断の記録

## 2026-11-03　一次対応の返答は「ツール呼び出しの強制」で構造化する

**決めたこと**：一次対応エージェントは自由文ではなく、`reply_to_teacher` ツールを必ず呼ぶ形で返す（kind = question / steps / escalate、steps は配列、疑わしい原因はタグ）。
**なぜ**：画面を「はい／いいえ」「直った／直らない」のボタンで組める。先生に文字を読ませる量を最小にでき、原因チップの初期値（「たぶんこれ」）も出せる。質問回数の上限（2問）もサーバー側で強制できる。
**保険**：APIキーが無い・失敗したときは playbook の手順をそのまま返す。AIが止まっても一次対応は成立する。

## 2026-11-03　Next.js 16 の Cache Components を使わない

**決めたこと**：`cacheComponents: false`。
**なぜ**：台帳JSONは毎リクエスト読み、日付シミュレーターは cookie で動く。Suspense 境界の設計に時間を使うより、6日間では素直な動的レンダリングのほうが安全。

## 2026-11-03　Webアプリを優先し、MCPサーバー化は後回し

**決めたこと**：まず Next.js のWebアプリとして動かす。エージェントのツール定義は、後からMCPで包める粒度にしておく。
**なぜ**：提出まで6日。審査員と先生が触れる形を最優先にする。MCPは「Claude活用」の目玉になり得るが、動かないものに目玉はない。
**捨てた案**：最初からMCPサーバーとして設計し、WebアプリをそのクライアントとしてMCP経由で接続する。

## 2026-11-03　架空校名を「県立あさひ台工業高等学校」にする

**決めたこと**：データ上の学校は架空の「県立あさひ台工業高等学校」。
**なぜ**：実在校の資料・名称を使わないため。検索で同名校は見つからなかった（似た名の実在校：竹台、日野台、麻溝台。いずれも別名）。
**注意**：人物・業者もすべて架空。コミット前フックで実在校名・人名らしき文字列を検出する。

## 2026-11-03　「視聴覚」という語を捨てる

**決めたこと**：役職・領域・部屋名に「視聴覚」を使わない。校内ICT担当／教室ICT／大型提示装置／ICT準備室 に統一。
**なぜ**：現場でも文科省の文書でも、いまの標準語彙はICT。「大型提示装置」は文科省の用語で、審査員への通りがよい。

## 2026-11-02　校務全般の引継ぎ → 教室ICTトラブルの一次対応に絞る

**決めたこと**：当初の「校務分掌の引継ぎエージェント（全分掌）」をやめ、校内ICT担当が毎週受けている「映らない」コールの一次対応に絞る。引継ぎは、対応の記録が溜まった結果として自動生成される副産物にする。
**なぜ**：
1. 「ベテランの知識をAIで整理して次の人へ」はテーマ1の参加者の多くが最初に思いつく形で、Discordにも中小企業版の同じ構想が出ていた。並ぶと埋もれる。
2. 中にいる人にしか見えない「足りないもの」は、ヘルプデスクではなく「2分で直して立ち去る対応は小さすぎて誰も記録しない」こと。ここに絞ると、記録の手間をゼロにする設計（1タップ）が核になる。
3. 教室ICTの領域には生徒の個人情報がほぼ入らない。当初案は個人情報のため「将来はローカルLLM」と言わざるを得なかったが、絞ったことで**来年4月に実際の学校でそのまま使える**。
4. 毎週起きる痛みのほうが、年1回の引継ぎより強い。デモも3分に収まる。
**捨てた案**：
- 全分掌の引継ぎエージェント（汎用的すぎる）
- 式典音響を顧問と放送部3年生が替わっても回せる仕組み（独自性は最も高いが年数回の出来事。「次の領域」として残す）

## 2026-11-02　知識はリポジトリ内のJSON、ベクトルDBは使わない

**決めたこと**：台帳・手順・履歴は `data/*.json`。1校ぶんは数万トークンに収まるので、必要な部分をそのまま文脈に渡す。
**なぜ**：人が読める・Excelに戻せる・ローカルLLMにも渡せる。断片検索より正確で、「基本的なRAGアプリ」と一線を画す。

## 2026-11-04　数字はAIに数えさせない（事実パック層）

**決めたこと**：癖の抽出と文書生成の前に、履歴・台帳を決定的に集計する層（`src/lib/agent/facts.ts`）を置く。Sonnet にはこの集計結果だけを渡し、「事実にない数字・機種・業者・日付を作らない」と指示する。APIキーが無いときは同じ事実パックから雛形を組み立てる。
**なぜ**：引継ぎ文書や購入計画は管理職・業者・次の担当が読む。1件でも数字が違えば信用を失う。集計はコードの仕事、言葉にするのがAIの仕事、と分ける。副産物として、AIなしでも文書が出る（学校のネットワーク事情に強い）。

## 2026-11-04　Sonnet 5.5 にはツール呼び出しの強制が効かない → 構造化出力

**決めたこと**：一次対応（Haiku 5.5）は `tool_choice: {type:"tool"}` で返答を構造化したままにする。癖の提案（Sonnet 5.5）は `output_config.format`（zod スキーマ）で JSON を受け取る。文書生成はストリーミングの素の Markdown。
**なぜ**：Sonnet 5.5 / Opus 5.5 は forced tool_choice を 400 で拒否する（Haiku 5.5 は受け付ける）。同じ「構造化して返す」目的でも、モデルごとに正しい手段が違う。LLM呼び出しは `src/lib/llm/` と `src/lib/agent/` に閉じているので、差し替えは局所で済む。

## 2026-11-04　却下した提案は覚えておく

**決めたこと**：`devices[].rejected_quirks` を追加。却下された提案は再提案しない。
**なぜ**：ICT担当が毎回同じ提案を却下する羽目になると、提案機能そのものが信用されなくなる。承認・却下の履歴が「人が最後に決めた」証拠にもなる。

## 2026-11-04　写真は保存しない。所見だけを残す

**決めたこと**：F5 の写真は端末で縮小してリクエストの中だけで使い、サーバーにもリポジトリにも保存しない。AIの所見（「電源ランプが橙で点滅」など1〜2文）だけがチケットの note に残る。写真ブロックは「直らない」の引き継ぎ画面の中にだけ出し、APIキーが無いときは出さない。
**なぜ**：教室で撮る写真には生徒が写り込みうる。「生徒の個人情報を持たない」設計を守るには、画像を持たないのがいちばん確実。ICT担当に必要なのは画像ではなく「何が見えたか」で、それは文章で足りる。使えない機能のボタンを先生に見せないのは、30秒しか待てない人への礼儀。

## 2026-11-04　現場の数字に合わせる。「癖」ではなく「確認ポイント」

**決めたこと**：ICT担当本人の聞き取りを受けて、①架空校を工業高校（県立あさひ台工業高等学校）にする ②履歴の件数を「呼ばれるのは月3件、先生が自分で直す分と事後報告がその外側にある」規模に作り直す ③先生向けの語を「癖」から「確認ポイント」に変える ④原因に「Wi-Fi・無線」を加える。
**なぜ**：本人の言葉は「機器の癖のようなものはない。あるのは、電子黒板の無線が切れていた、コネクタの物理破損、HDMI端子が複数あるときの接続ミス」。これは機器の個性ではなく、毎回確認すべき点。「癖」と呼ぶと当事者の実感から離れる。件数も、百回という盛った数字より「月3回＋記録されない事後報告」のほうが、記録が残らない問題の説明としてずっと強い。生徒端末のトラブル（パスワード忘れ等）は多いが、個人情報を伴うため対象外と明記した。

## 2026-11-04　製品名を「映らないノート」に

**決めたこと**：「映らない！」から「映らないノート」へ。英語識別子 `utsuranai` はそのまま。
**なぜ**：「映らない！」は呼び声として強いが、この製品の本体は、押すたびに溜まって次の担当に渡る記録のほう。名前に「ノート」を入れて、呼び声と蓄積の両方を1語で言う。候補「教室カルテ」は分かりやすいが、先生が最初に押す瞬間の言葉が消える。

## 2026-11-04　文書生成は長考させない

**決めたこと**：書類の下書き（Sonnet 5.5 ストリーミング）は `thinking: { type: "between_tools" }` で長考を切る。`effort` は medium のまま。
**なぜ**：既定のままだと最初の1文字が出るまで59秒、全文で87秒かかった。読みながら待てるのがストリーミングの価値なのに、1分間白い画面では意味がない。切ると1.8秒で流れ始め、25秒で終わる。内容は事実パックの数字を言葉にする作業なので、長考の恩恵が小さい。なお `{type:"disabled"}` はこのモデルでは 400 で拒否され、エラー文が `between_tools` を案内してくる。

## 2026-11-06　画面のデザイン基盤を1つにする（ユニバーサルデザイン）

**決めたこと**：全画面を共通の部品（`card` / `btn` / `chip` / `eyebrow` など、`src/app/globals.css`）で組む。文字は UD フォント（BIZ UDPGothic）優先・本文 17px・行間 1.6。配色は白地に本文 14:1、補助文 5:1 以上。押せるものは高さ 48px 以上。フォーカスは 3px の輪郭。意味は色だけで伝えない（「たぶんこれ」「予備機：」「予備機で継続中」など文言を併記）。`prefers-reduced-motion` で動きを止める。ブランドマーク（スクリーンと緑の点）を追加。
**なぜ**：先生は焦っている状態でスマホを見る。見分けやすい文字と大きな押し場所が、速さと誤操作の少なさに直結する。色覚の違いや老眼にも配慮が要る（職員室の年齢層は広い）。ICT担当側は情報量が多いので、カードと見出しで区切り、数字は等幅で揃える。
**捨てたもの**：装飾的なグラデーションや影の多用、アイコンだけのボタン。
