# 「映らないノート」仕様書（下書き v0.1）

教室ICTサポートエージェント — Built with Claude: Japan 2026 提出作品
作成：2026-11-03　状態：下書き（セッション①「仕様の言語化」後に v0.2 へ）

---

## 1. 一言で

教室で「プロジェクターが映らない」が起きたとき、**その教室の機器を知っているエージェント**が先生の一次対応を助け、直した瞬間の1タップが**次のICT担当への引継ぎ**として自動的に溜まっていく仕組み。

タグライン候補：
- 「知識を人ではなく、役職に残す」
- 「引継ぎファイルは書かない。1年、タップするだけ」

テーマ：1「あなたにしかない深さを。」（主）／2「本来、誰にでも届くべきものを。」（人手不足・兼務の増加に触れる）

---

## 2. 課題

### 2.1 足りないもの（中にいる人だから見えること）

校内ICT担当は年に百回以上、教室の機器トラブルを直している。だが **2分で直して立ち去る対応は、小さすぎて誰も記録しない**。知識は担当者の頭にだけ残り、異動と同時に学校から消える。次の担当は同じ百回をやり直す。

足りないのはヘルプデスクではなく、**記録の手間をゼロにしたうえで、教室ごとの文脈を持った知識の置き場**。

### 2.2 困っている4人

| 人 | 場面 | 失うもの |
|---|---|---|
| 呼ぶ先生 | 授業開始直後、大型提示装置が映らない | 授業の5〜10分、生徒の前での焦り |
| 生徒 | その教室 | 年間で積み上がる授業時間 |
| ICT担当 | 自分の授業中に呼ばれる | 自分の授業の中断、放課後の修理対応 |
| 次のICT担当 | 4月 | 百回ぶんの学習をやり直す |

### 2.3 数字（ICT担当本人の実感。11/4 聞き取り）

- 呼ばれる頻度：**月 3 回ほど**（年 30 回前後）。先生が自分で直して終わる分と、あとからの事後報告がこの外側にある
- 新しい機器・システムが入った直後はいっせいに増える
- 繰り返す中身：電子黒板の無線投影（Wi-Fi）が切れていた／ケーブルのコネクタの物理破損／HDMI端子が1〜3個ある機器での接続ミス
- 1回あたり失われる時間：呼ぶ側 5〜10 分、ICT担当 10〜15 分（移動込み）
- 架空校データはこの感覚に合わせる：4〜11月で 75 件、うちICT担当が関わるのは 22 件（月 3 件）、残りは先生・生徒の自己解決
- 対象外として多いもの：生徒端末のトラブル（パスワード忘れなど）。個人情報を伴うため本作では扱わない

### 2.4 地域の文脈

福井県の県立学校では教員が数年ごとに学校間で異動する。少子化による統廃合・教員減で、1人が複数の分掌を兼ねる方向にあり、属人性の問題は今後むしろ悪化する。

## 3. 対象外（作らないもの）

- 授業・学習・生徒向けの機能（これは「教育のAI」ではなく「先生の事務仕事のAI」）
- 生徒の個人情報を扱う機能
- 校務支援システムとの連携
- ローカルLLMの実装（LLM呼び出し層を1か所に閉じ、将来差し替え可能にするに留める）
- MCPサーバー化（Webアプリを優先。ツール定義は後からMCPで包める形にしておく）
- 機器の遠隔制御

## 5. 機能（優先順）

### F1. 教室の一次対応（MVP）
- 教卓のQR → 教室ページ。教室名・機器構成・**静的カード**（既知の癖、ケーブルの場所、予備機の場所）が**AIなしで**常に表示される
- 症状チップ（映らない／音が出ない／反応しない／ちらつく／その他）を押す
- エージェントが最大2問だけ聞き、その教室の機器に合わせた手順を1〜3ステップで返す
- 「直った」「直らない」のボタン

### F2. 1タップ記録（MVP）
- 「直った」→ 原因チップ（入力切替／ケーブル・アダプタ／電池・リモコン／設定／機器故障／その他）を1タップ。文章入力は任意
- `incidents` に自動保存（日時・教室・機器・症状・原因・所要分・誰が直したか）
- 「直らない」→ 状況つきチケットをICT担当へ。併せて **予備機の案内**（「ICT準備室の予備機B-2で授業を続けてください」）

### F3. ICT担当ダッシュボード（MVP）
- 未対応チケット一覧
- **教室の癖の抽出**：履歴からClaudeが「2年3組は停電後に入力がVGAへ戻る」などを生成し、静的カードへの反映を提案（担当が承認）
- 傾向：「電気科2年は今学期8件すべてケーブル。教卓側の端子交換を推奨」
- 消耗品・寿命：ランプ時間、導入年、保守契約の期限
- **守られた授業分数**（一次対応で自己解決した件数 × 想定分数）

### F4. 書類の下書き（差別化）
- 備品購入計画の下書き（根拠：トラブル件数、導入年、寿命）
- 業者への修理依頼文
- **引継ぎ文書**：日付を年度末に進めて「引継ぎ」→ 1年分の履歴・癖・業者・予備機・年間の山場を、次の担当向けの文書として生成

### F5. 写真による補助判定（差別化、小さく）
- 「直らない」時に写真を1枚。状態表示・ケーブル・端子を見て原因候補を絞る
- 製品の主役にしない（「画像解析ツール」に見せない）
- 実装：引き継ぎ画面（直らない→予備機案内）の中にだけ出る。端末側で長辺1024pxに縮小、サーバーは保存しない。所見（文章）だけがチケットの note に残る。APIキーが無いときはブロック自体を出さない
- 画面に「生徒が写らない向きで」と書く。プロンプトでも人物に触れないよう指示

### F6. 日付シミュレーター（デモ必須）
- 画面上の「今日」を動かせる。年度末の引継ぎ生成、秋の購入計画のデモに使う

### F7. Excel台帳の取り込み（ストレッチ）
- 既存の備品台帳Excelを構造化出力でスキーマに変換。他校が始めるときの入口

### F8. MCPサーバー化（後回し）
- F1〜F4のツール定義をMCPで包み、Claude Codeから台帳操作・起案生成ができるようにする

## 6. データ構造

すべてリポジトリ内のJSON（必要なら人が読むためのMarkdownも生成）。DBなし。人が読め、Excelに戻せ、ローカルLLMにも渡せる。

```
data/
  school.json        架空校の基本情報、年度、行事
  rooms.json         教室
  devices.json       機器
  playbooks.json     機種×症状 → 手順
  incidents.json     トラブル履歴
  vendors.json       業者（架空）
  spares.json        予備機・消耗品の在庫と場所
```

### rooms
`id, name, floor, building, qr_code, devices[], notes_static（静的カードに出す文）`

### devices
`id, room_id, kind（projector | display | speaker | mic | doc_camera | pc）, maker, model, installed_year, inputs[]（HDMI1, HDMI2, VGA, USB-C…）, default_input, cable_location, remote_location, quirks[]（担当が承認した癖）, lamp_hours, warranty_until, vendor_id, status（active | repair | spare）`

### playbooks
`id, device_kind, model?（null なら機種共通）, symptom, questions[]（最大2問）, steps[], escalate_when, spare_hint`

### incidents
`id, datetime, room_id, device_id, symptom, cause_tag, resolved（self | spare | ticket）, resolved_by（teacher | ict | student）, minutes_lost, note?, photo?（任意）, ticket_status`

### vendors
`id, name（架空）, contact_role, covers[]（device kinds / models）, contract_until`

### spares
`id, kind, model, location（ICT準備室 棚B-2 など）, qty, consumable（bool）`

## 7. エージェント設計

### 7.1 ツール（Anthropic SDK のツール呼び出し。後にMCPで包める粒度）

| ツール | 役割 |
|---|---|
| `get_room_context(room_id)` | 教室・機器・静的カード・最近の履歴 |
| `find_playbook(device_id, symptom)` | 該当手順 |
| `record_incident(...)` | 1タップ記録 |
| `open_ticket(...)` | ICT担当へ |
| `find_spare(kind, near_room)` | 予備機の案内 |
| `summarize_patterns(range)` | 傾向・癖の抽出（F3） |
| `draft_document(kind, inputs)` | 購入計画・依頼文・引継ぎ（F4） |

### 7.2 モデルの使い分け

| 目的 | モデル | 理由 |
|---|---|---|
| 教室の一次対応 | Haiku 5.5 | 30秒以内。安い。手順は playbook が持つので推論は軽い |
| 癖の抽出、購入計画、引継ぎ文書 | Sonnet 5.5（必要なら Opus 5.5） | 推論の深さ。頻度は低い |
| 写真判定 | Sonnet 5.5（画像入力） | 補助のみ |
| 台帳の取り込み（F7） | Sonnet 5.5 ＋ 構造化出力 | 雑多なExcel → スキーマ |

1校ぶんの台帳＋手順は数万トークンに収まる想定。プロンプトキャッシュで毎回渡し、ベクトル検索は使わない（設計判断として README に書く）。

### 7.3 フォールバック

- API不通・遅延 → 静的カードと playbook の手順をそのまま表示（AIなしでも一次対応は成立する）
- 不明 → 予備機案内＋チケット。推測で手順を増やさない

### 7.4 プロンプト方針

- 返答は3ステップ以内、1ステップ1行、場所は具体名（「教卓右の引き出し」）
- 分からないことは分からないと言い、予備機とチケットに誘導
- 専門語を避ける（先生は急いでいる）

## 8. 画面

1. **教室ページ**（/room/[id]）：静的カード → 症状チップ → 対話（最大2問）→ 手順 → 直った／直らない
2. **記録**：原因チップ → 完了。直らない → 写真（任意）→ 予備機案内 → チケット送信
3. **ICT担当ダッシュボード**（/admin）：チケット、癖の提案（承認ボタン）、傾向、寿命、守られた授業分数
4. **書類**（/admin/docs）：購入計画／依頼文／引継ぎ の生成と編集
5. **日付シミュレーター**：ヘッダーに「今日」。デモ用

スマホ優先。ボタンは大きく、文字入力は最後の手段。音声入力はブラウザ標準があれば使う（必須ではない）。

## 10. ダミーデータ計画（11/3 に作成）

架空校：**県立あさひ台工業高等学校**（仮。実在しないことを確認する）
- 教室：普通教室 18、特別教室 8（実習室・理科室・ICTルーム・体育館・多目的室 等）、職員室、ICT準備室
- 機器：大型提示装置（プロジェクター3世代混在、電子黒板2機種）、スピーカー、ワイヤレスマイク、書画カメラ。導入年をばらす
- 癖：10〜15件（停電後に入力が戻る、特定端末でUSB-Cが認識しない、リモコンが隣室と混信 等）
- 履歴：1年分 120〜180件。月ごとの山（4月・9月・行事前・寒い朝）、原因分布は 2.3 の推定に合わせる
- 行事：入学式、全校集会、体育祭、文化祭、修学旅行、入試、卒業式
- 業者：2〜3社（架空）、保守契約の期限
- 登場人物：全員架空。実在の人名・校名・電話番号を入れない

作り方：先生が1年の実感を口述 → Claude Code のサブエージェント `data-author` が JSON を生成 → 先生が「それらしさ」を点検。

## 17. 提出チェックリスト（11/4 キックオフ文字起こしより）

- 期間中に新規に始めたものだけ。**事前に作った仕様書・構想は使ってよい**（コードは不可）

- 審査の見どころ（運営の言葉）：
  - インパクト：**当事者か**、日本特有か、問題定義が正しいか、**ハッカソン後も使えるか**
  - デモ：**前提知識がない人が理解できるか**、最後まで見たくなるか
  - Claude活用：どれほど創造的か、**他のツール・機能・モデルとどう組み合わせたか**
  - 深さと実行：試行錯誤の跡、実際の利用者のことが丁寧に設計されているか（**リポジトリ内で見る**）
- テーマ1の例として運営が挙げた形：「次の人に受け継ぐための形」「授業で当たり前だと思ってきた不便を、妥協しなくていい便利なものに変える」 → 本作はこの2つに正面から当たる

### 17.1 追記（11/4 夜。キックオフ全文とセッション1・2の文字起こしより）

- **APIクレジットと Max プランは、キックオフ直後にメールで配られる一回限りのコード**。メール（迷惑メール含む）を確認する。コンソールの申請フォームとは別経路の可能性がある
- 応募 5,541 件中 250 チーム（倍率22倍）。Claude Code 経験者 140、上級 65、初心者 37。分野は医療・教育・農業・建設・自治体など
- 海外ハッカソンの入賞者はほぼ非エンジニア（弁護士・医師・道路鑑定士・音楽家）。運営の結論は「コードを書ける人より、課題を一番よく知る人が強い」「課題を言葉にできるかが制約」 → 本作の強みは「ICT担当本人が作っている」こと。README と動画の冒頭でこれを言う

### 17.2 追記（11/5。セッション3 大谷「ゼロから作るもの」ライブデモの文字起こしより）

- やり方：まず**一番見せたい1機能だけ**を最短で動く形にし、触ってから肉付けする。「ハッカソンで評価されるのは完成品。未完成の大作より、小さく完成したもの」。時間配分は先に区切る（設計→実装→仕上げ）
- 壁打ちは文字より画像（アーティファクトの設計書は画像6：文字4）。認知負荷を下げる。実装の中身は見ず、できたものを触ってフィードバックだけ人が返す
- イシュー駆動：目的・ゴール・実装方法を issue に残し、AI が issue を見て進む。人が指示を忘れても記録が残る → 本作では `docs/DECISIONS.md` と `docs/BUILD_LOG.md` がその役。「深さと実行」はここを見せる
- レビューは二段（厳しいレビュー → 「この issue はこれだけ通ればよい」と観点を絞るレビュー）。本作の hurry-reviewer は後者
